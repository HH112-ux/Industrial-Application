# 智造协同 MES 系统介绍（重构目标态）

本文描述重构完成后系统应当具备的形态，面向第一次接触本项目的读者。施工计划与阶段验收见 [REFACTOR-PLAN.md](REFACTOR-PLAN.md)，架构取舍见 [ENGINEERING-DESIGN.md](ENGINEERING-DESIGN.md)。

文中每项能力标注状态：

- **已落地**：当前代码已经实现并有测试或实机验证
- **重构后落地**：目标状态，当前代码尚未实现

> 统计口径：截至 2026-11-11，后端 280 个测试（269 个单元测试 + 11 个 Testcontainers 集成测试），25 个 Flyway 迁移，21 张表 + 5 个只读视图（含 S1 设备凭证表、S2 遥测表、S3 工单状态历史表与报工幂等键、S4 工艺工序表、S5 排程结果表、S6 物料预占表与外部身份映射表、S8 两张 AI 审计表；S6 为既有表补充身份与车间字段），管理端 12 个页面。与四份设计文档不一致时，以代码与迁移为准。

---

## 1. 一句话定位

面向离散制造车间的 MES：把生产计划拆成工单，管住工单从开工、报工、质检到完工的状态与数量，并把设备状态与遥测接进同一条业务链路。

它服务的是一间工厂内部的计划、执行与设备协同，不是跨工厂 SaaS，也不是 APS 排程器。

## 3. 能力地图

### 3.1 设备接入与状态

| 能力 | 现状 | 状态 |
|---|---|---|
| MQTT 设备接入 | 真实 Paho 连接，订阅 `factory/devices/+/status` | 已有 |
| 断线恢复 | 持久会话 + 重连后重订阅 + 指数退避（1s 起，最长 60s，不再放弃重试） | 已落地（S1） |
| 设备在线判定 | `last_seen_at` + 在线阈值，接口返回 `online`，不再靠状态字符串猜 | 已落地（S1） |
| 设备凭证 | `key_id + HMAC-SHA256`，密钥 AES-256-GCM 加密存储，可签发与吊销 | 已落地（S1） |
| 上报去重 | 幂等键短路重复上报，`eq_telemetry.ingest_key` 唯一索引兜底 | 已落地（S2） |
| 模拟遥测 | 默认关闭；开启后数据标记 `source=SIMULATED`，不会伪装成真实数据 | 已落地（S1） |
| 遥测历史 | 按时间范围查询历史采样，默认 24 小时、最多 1000 条，保留 90 天 | 已落地（S2） |

比重构前强在哪：过去断线重连会丢订阅、首次连不上就放弃、遥测是随机数且无法区分真假；现在这些行为都有明确语义和可验证结果。

### 3.2 工单执行

| 能力 | 现状 | 状态 |
|---|---|---|
| 工单全流程 | 开工、报工、质检、完工，联动计划完成 | 已有 |
| 并发保护 | 乐观锁，两个请求同时开工只有一个成功 | 已落地（S3，后端） |
| 状态留痕 | 每次流转写入 `wo_status_history`，可查时间和操作人；管理端工单列表提供流转记录时间线 | 已落地（S3 后端，S7 前端） |
| 报工数量校验 | 数量必须为正、合格数与不良数之和等于报工数、累计不超量 | 已落地（S3） |
| 报工幂等 | 同一幂等键重复提交不重复累加，重试返回首次结果 | 已落地 |
| 状态机语义 | `PENDING → IN_PRODUCTION → PENDING_QC → FINISHED`，质检不合格退回 `IN_PRODUCTION` | 已有且保持不变 |

比现在强在哪：重构前两个请求可以同时把同一张工单开工，状态变化没有任何记录，报工数量可以填负数或超过订单量。S3 之后并发重复流转、无留痕、数量越界都已被守住；报工幂等也已落地，弱网重试不会重复累加。

### 3.3 工艺与 BOM

| 能力 | 现状 | 状态 |
|---|---|---|
| 工艺主数据与审批 | 草稿、提交、通过、驳回；同一 `process_no` 多行表达版本 | 已有（版本化 S4） |
| 工序建模 | 工艺版本下挂单级工序，带顺序、设备类型与标准工时；不做工步 | 已落地（S4） |
| BOM 版本 | 不再单独维护 BOM 版本，BOM 通过 `process_id` 归属工艺版本行 | 已落地（S4，A 方案） |
| 发布冻结 | 发布后的工艺版本不可修改，只能复制下一版草稿 | 已落地（S4） |
| 齐套绑定版本 | 齐套按工单锁定的工艺版本计算，不受后续改版影响 | 已落地（S4） |

比 S4 之前强在哪：此前工艺只有描述字段，齐套取「全局最新 BOM」，改版后历史工单的齐套口径会漂移；现在版本由工艺行固定，BOM 挂在 `process_id` 下，齐套口径不再随改版变化。

### 3.4 计划与排产

| 能力 | 现状 | 状态 |
|---|---|---|
| 计划管理 | 建计划、更新、下达工单 | 已有 |
| 下达指定工艺 | 下达时显式选择已发布工艺，不再默认取第一条 | 已落地（S5） |
| 有限产能排产 | 按设备可用时间与工序工时给出可解释的排程建议 | 已落地（S5） |
| 自动排产求解 | 不做，不引入 APS 求解器 | 明确不做 |

### 3.5 权限、审计与运维

| 能力 | 现状 | 状态 |
|---|---|---|
| 登录与角色 | JWT + `ADMIN`/`USER`/`WORKER` 三级取值；工单开工/报工允许三种角色，质检仅 `ADMIN`/`USER`，计划派工与其余管理动作仅 `ADMIN`；SSO 账号走本地密码登录时返回「该账号需使用企业微信扫码登录」 | 已落地（S6 + 后续安全迭代） |
| 身份即时失效 | 过滤器每次请求查库校验启停与令牌版本，禁用或改密后下一次请求 401；自助改密与管理员重置密码均递增版本 | 已落地（S6） |
| 车间数据域 | 非管理员按 `workshop_scope` 过滤设备、计划与工单；未分配时看不到任何车间数据（deny-by-default），由管理员在用户管理页显式分配；列表自动过滤，详情跨车间 403，管理端看板随列表受限 | 已落地（S6） |
| 登录限流 | 抽成 `LoginRateLimiter` 端口，当前为单实例本地实现；多实例部署必须替换共享存储实现，未接 Redis | 已落地（S6） |
| 写操作审计 | 记录写操作日志，标注成功/失败与错误摘要，支持按操作人、路径与日期范围查询 | 已有（S6 增强查询，V20 补结果字段） |
| 指标与可观测性 | 设备在线数/在线率、遥测上报与处理耗时、报工计数、工单节拍、齐套率；请求日志带 `traceId` | 已落地（S7） |

## 4. 端到端主流程

以一张工单为例，从接单到完工：

```text
计划创建（PENDING 计划）
   │  计划员录入产品、数量、交期
   ▼
下达工单 ── 选择已发布工艺 ── 生成工单号 WO-
   │
   ▼
齐套校验 ── 按工单工艺/BOM 版本算需求 ── 库存不足则拒绝开工
   │
   ▼
开工 ── 乐观锁抢占 ── PENDING → IN_PRODUCTION ── 写状态历史
   │
   ▼
报工 ── 数量校验 + 幂等 ── 累计合格/不良 ── 写报工记录
   │
   ▼
提交质检 ── IN_PRODUCTION → PENDING_QC ── 写状态历史
   │
   ├─ 质检通过 ── PENDING_QC → FINISHED ── 回写计划完成
   └─ 质检不通过 ── PENDING_QC → IN_PRODUCTION ── 返工后重新报工
```

关键校验点：

1. 下达前必须有已发布工艺；下达后工单绑定该工艺版本。
2. 开工前校验工艺存在、设备可用、物料齐套。
3. 开工与质检流转使用乐观锁，冲突请求返回可识别的错误而不是静默覆盖。
4. 报工数量必须为正，合格数与不良数之和不得超过剩余数量。
5. 质检不合格退回生产，不产生新的工单。
6. 工单完工后联动计划状态，计划下所有工单完成后计划才完成。

## 5. 技术形态

**分层与模块**：后端采用模块化单体，单一部署单元、单一数据库，包边界按业务域划分（identity、device、masterdata、process、planning、execution、maintenance、audit、ai）。调用方向为 Controller → Application Service → Domain → Infrastructure，跨模块只走应用服务，不直接访问对方 Mapper。

当前代码仍是按技术分层的包结构（controller/service/gateway/security/entity/mapper），模块化边界随 S4–S6 逐步收敛；不改变现有包结构也能运行。

**数据域**：MySQL 保存设备、物料、物料预占、工艺、BOM、计划、工单、报工、质检、维保、用户、外部身份映射、序列、审计，以及 S1 新增的设备凭证与 S2 新增的遥测时序。遥测先落 MySQL 单表，保留 90 天，通过 Repository 端口预留迁移时序库的可能。

**外部依赖**：

- MySQL 8：业务数据与迁移（Flyway）
- Redis 7：缓存；S6 起承担限流
- MQTT Broker（Mosquitto）：设备上行；S1 起使用持久会话
- AI 模型 API：S8 已落地，默认关闭（`ai.enabled=false`），不进入主链路

**部署**：本地开发为后端 8080、管理端 5173（Vite）；容器形态由 `docker-compose.yml` 提供 MySQL、Redis、Mosquitto、后端、前端五个服务，前端容器映射 8081。生产环境需要替换 JWT 密钥、数据库密码与设备凭证主密钥，并配置反向代理与 HTTPS。

## 6. 边界与不做的事

已决策的边界：

1. 不拆分微服务，保持模块化单体。
2. 不做完整多租户，只做车间数据域；不引入 `tenant_id`。
3. 不引入 Kafka/RocketMQ，设备接入继续用 MQTT；跨服务一致性预留发件箱表。
4. 不做 APS 全局最优排程，只做有限产能贪心排程，结果可解释。
5. 工艺只建模到单级工序，不做工步。
6. 不做预测性维护。
7. 不做全自动视觉质检。
8. 不允许模型直接排产、直接修改工单状态或数量。
9. 遥测先落 MySQL，不引入专用时序数据库；达到容量边界再迁移。
10. AI 不作为主链路前置条件，默认关闭。

## 7. 质量承诺

- **提交门禁**：本地 `commit-msg` 钩子按 Conventional Commits 校验；CI 对推送范围再校验一次。
- **构建门禁**：后端 `mvn test` 必须通过；管理端 `npm ci && npm run build` 必须通过。
- **测试策略**：以 Mockito 单元测试为主，覆盖状态机、齐套口径、编号生成、认证、设备签名与幂等；另有一层薄集成测试，用 Testcontainers 起 MySQL 验证 Flyway 迁移、状态机合法/非法流转与真实并发开工。单元测试负责分支覆盖，集成测试只守住最容易回归的两条路径，不铺全量数据库用例；Docker 不可用时集成测试整类跳过，不阻塞构建。
- **可观测性**：提供 `/actuator/health`、`/actuator/info`、`/actuator/metrics` 与带 `traceId` 的请求日志；业务指标包括设备在线、遥测上报、报工、工单节拍与齐套率。空分母指标返回 `NaN` 表示未定义，不用 0 或 100% 掩盖缺数据。告警阈值不在本阶段范围。
- **不变量**：工单状态语义、齐套口径、编号规则、鉴权与审计、AI 旁路约束写在 [ENGINEERING-DESIGN.md](ENGINEERING-DESIGN.md) 第 7 节，重构过程中不得静默改变。

## 8. AI 能力（P2，已落地）

三个场景已落地：设备异常归因与处置建议、自然语言报工草稿、生产数据问答（Text-to-SQL）。AI 全部处于旁路：`ai.enabled` 默认 false，关闭时三个 `/api/ai/**` 端点返回 HTTP 503 + 业务码 503，其余功能不受影响；开启后默认使用离线假模型，CI 不需要网络与密钥。AI 只调用只读工具，输出只作为建议文本，不得直接写库；模型超时、报错或返回非法内容时降级为「建议暂不可用」，不影响下单、报工与状态流转。自然语言报工只产出表单草稿，始终要求人工确认后再调用现有报工接口。Text-to-SQL 仅对 ADMIN 开放，只允许单条 SELECT 查询 5 个只读视图，强制行数上限并记录 SQL 审计。

详细工具清单与降级策略见 [ENGINEERING-DESIGN.md](ENGINEERING-DESIGN.md) 第 8 节。

## 9. 从「能演示」到「能守住不变量」

这个系统的变化不在于页面变多，而在于同一件事被重复做时结果是否一致。

演示阶段可以接受：断线后重启、遥测随机生成、两个请求同时开工、报工填多少算多少、改一次 BOM 历史齐套口径跟着变。这些行为在演示时看不出来，但在车间里每天都会发生。

重构后的目标是：连接断了自己恢复，数据来源可区分，同一张工单不能被并发改写，报工数量有边界，工艺和 BOM 的版本在工单执行期间固定，凭证可以吊销，提交和构建有门禁。这些能力逐条对应 [REFACTOR-PLAN.md](REFACTOR-PLAN.md) 里的验收项，而不是靠文档描述。
